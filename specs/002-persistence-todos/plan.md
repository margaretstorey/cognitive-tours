# Implementation Plan: Phase 2 — Persistence

**Branch**: `002-persistence-todos` | **Date**: 2026-05-21 | **Spec**: [spec.md](./spec.md)

**Input**: Feature specification from `/specs/002-persistence-todos/spec.md`

## Summary

Add SQLite persistence to the Shrimp MVP via Prisma ORM and Next.js Route Handlers. All waypoints,
edges, and tours are stored in a local SQLite database and loaded on startup with a single bulk API
call. All mutations follow an optimistic update strategy: the UI updates immediately and the write
completes in the background; on failure the state reverts and an error message is shown. The
existing mock data is used as seed data on first run when the database is empty.

## Implementation Notes

### Prisma client singleton

Next.js hot-reload in dev creates multiple module instances. The canonical pattern to avoid
exhausting SQLite connections is a module-level singleton with global caching in development:

```ts
// app/lib/db.ts
import { PrismaClient } from '@prisma/client';

const globalForPrisma = global as unknown as { prisma: PrismaClient };
export const prisma = globalForPrisma.prisma ?? new PrismaClient();
if (process.env.NODE_ENV !== 'production') globalForPrisma.prisma = prisma;
```

### Optimistic update pattern

Each mutation handler in `ShrimpApp` follows this shape:

1. Snapshot the current state slice.
2. Apply the change to local state immediately.
3. Call the API in the background (no `await` blocks the handler).
4. On error: restore the snapshot and set `errorMessage`.

The snapshot approach is simpler and less error-prone than trying to invert the operation.

### Startup loading state

`ShrimpApp` gains a `loadState: 'loading' | 'ready' | 'error'` piece of local state.
A `useEffect` with an empty dependency array fires once on mount, calls `GET /api/data`,
populates the three state arrays, then transitions to `'ready'`. While `loadState === 'loading'`,
the component renders a centered spinner instead of the three-panel layout.

### Seeding

`GET /api/data` checks whether any waypoints exist in the database. If the count is zero, it
inserts all records from `INITIAL_WAYPOINTS`, `INITIAL_EDGES`, and `INITIAL_TOURS` (preserving
IDs) before returning the full dataset. This is the only place seeding occurs.

### TourWaypoint ordering

`Tour.waypointIds` in AppState is an ordered array. In the database this is stored as a
`TourWaypoint` join table with an `order` integer column. When converting from Prisma to AppState,
records are sorted by `order` and mapped to `waypointIds: string[]`. When writing a tour, the
array index becomes the `order` value.

### Error display

A new `errorMessage: string | null` state in `ShrimpApp` is set when any background write fails
and cleared automatically after 5 seconds. The message renders as a fixed banner at the top of
the screen (above the TourBar), visible regardless of which panel the user is looking at.
